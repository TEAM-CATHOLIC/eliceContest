## 1. 개요 (Background)

PRD의 MVP(메일 분석 → 계정 후보 → 탈퇴 화면 안내)를 2주 안에 연속 데모로 만들기 위한 기술 스택을 정한다.

* **현황:** 기능 범위는 PRD로 확정됐고, 언어·GUI·브라우저 조작·메일 분류 기술이 미정이다.
* **목표:** Mac/Windows에서 돌아가고, 메일 원문과 인증정보가 기기 밖으로 나가지 않으며, 10영업일 안에 데모가 가능한 스택.

## 2. 후보군 (Candidates)

가장 큰 결정은 **언어**와 **브라우저 조작 방식**이다. 나머지는 이 둘이 정해지면 따라온다.

**언어 / GUI**

1. **Python + PySide6:** AI·브라우저 자동화 라이브러리를 한 프로세스에서 바로 쓴다. Qt 기반이라 성숙하다.
2. **Python + Flet:** 선언형 UI라 빠르게 만들 수 있다. 생태계는 상대적으로 작다.
3. **Kotlin + Compose Multiplatform + Koog:** UI 품질과 타입 안정성이 좋다. 브라우저 조작은 Node.js 기반 Playwright MCP를 별도 프로세스로 붙여야 한다.

**브라우저 조작 방식**

1. **새 창 + 앱 전용 프로필 (Playwright):** 화면에 보이는 새 Chrome 창을 띄우고, 로그인은 사용자가 직접 한다.
2. **사용자가 쓰던 Chrome에 연결 (CDP):** 기존 로그인 세션을 그대로 쓴다.
3. **Chrome 확장 프로그램:** 사용자 브라우저 안에서 사이트별 권한으로 동작한다.

## 3. 상세 비교 (Comparison)

### 3.1 브라우저 조작 방식

| 항목 | 새 창 + 전용 프로필 (추천) | 기존 Chrome 연결 | 확장 프로그램 |
| :--- | :--- | :--- | :--- |
| **보안** | ⭐⭐⭐⭐⭐ 새로 로그인한 서비스만 접근 | ⭐ 모든 로그인 세션 노출 | ⭐⭐⭐⭐ 사이트별 권한 |
| **구현 난이도** | 낮음 | 높음 (Chrome 재시작, OS별 처리) | 높음 (확장 + 앱 통신) |
| **사용자 편의** | 보통 (서비스마다 로그인 1회) | 좋음 | 좋음 |
| **안정성** | 높음 (창을 앱이 통제) | 낮음 (사용자 탭·확장과 충돌) | 보통 |

### 3.2 언어 / GUI

| 항목 | Python + PySide6 (추천) | Python + Flet | Kotlin + Compose + Koog |
| :--- | :--- | :--- | :--- |
| **AI·브라우저 연동** | 같은 프로세스에서 직접 | 같은 프로세스에서 직접 | MCP 서버를 별도 프로세스로 |
| **난이도** | 보통 | 낮음 | 높음 |
| **커뮤니티** | 매우 활발 | 보통 | 제한적 (에이전트 쪽) |
| **배포** | PyInstaller, OS별 빌드 | PyInstaller 계열 | 네이티브 패키징 + Node.js 필요 |

### 🔍 주요 차이점

- **기존 Chrome 연결**은 편하지만, 유출 대응 서비스가 사용자의 모든 세션을 AI에 여는 구조라 제품 신뢰와 정면으로 부딪힌다. 또 Chrome이 기본 프로필의 원격 디버깅을 막는 쪽으로 바뀌어서 기술적으로도 불안정하다.
- **Kotlin**은 모바일 계획이 있을 때 강점이 크지만, 이번 범위는 데스크톱뿐이다. 브라우저 조작을 위해 Node.js 프로세스를 따로 띄우는 비용만 남는다.

## 4. 최종 결정 및 근거 (Decision & Rationale)

### 🏆 선정 결과

| 영역 | 선택 | 한 줄 이유 |
| :--- | :--- | :--- |
| 언어 | **Python** | 메일 분류, 임베딩, 브라우저 자동화를 한 언어·한 프로세스로 처리 |
| GUI | **PySide6** | Mac/Windows 모두 성숙하고, 백그라운드 작업(분류·브라우저)과 UI 분리가 쉬움 |
| 브라우저 조작 | **Playwright (Python), 새 창 + 앱 전용 프로필** | 사용자 세션을 건드리지 않고, 설치된 Chrome 실행파일만 빌려 써서 용량 부담이 작음 |
| 브라우저 에이전트 | **플레이북 기반 스크립트 + 막힐 때만 LLM** | 대표 3곳은 경로가 정해져 있어 스크립트가 빠르고 정확함. 셀렉터가 깨질 때만 화면의 링크·버튼 요소를 추려 LLM에 주고, LLM이 고른 요소를 코드가 규칙 검사 후 클릭 |
| 메일 파싱 | **Python 표준 `mailbox`, `email`** | MBOX/EML을 외부 의존성 없이 로컬에서 처리 |
| 메일 분류 (로컬 분류기) | **사전학습 다국어 문장 임베딩(고정) + scikit-learn 로지스틱 회귀** | 데이터 400건 내외로 학습 가능. 로컬에서 돌아 메일 원문이 나가지 않음 |
| 규칙 엔진 | **도메인 정규화 + 키워드 규칙** | 확실한 가입·탈퇴 표현은 AI 없이 처리해 오분류를 줄임 |
| 저장소 | **SQLite (로컬)** | 후보, 사용자 라벨, 탈퇴 진행 상태를 파일 하나로 관리 |
| 배포 | **PyInstaller, OS별 빌드** | 데모용 실행파일을 Mac/Windows 각각 만들 수 있음 |

선정 이유는 다음과 같다.

1. **개인정보:** 메일 분류가 전부 로컬에서 끝나고, 브라우저는 사용자 세션과 분리된다. PRD의 "외부 전송 0건"과 "승인 없는 탈퇴 0건"을 구조로 보장한다.
2. **생산성:** 하나의 Python 프로세스 안에서 모든 기능이 연결돼서 2주 안에 통합 데모가 가능하다.
3. **안정성:** 브라우저 에이전트를 완전 자율형(browser-use 등)으로 두지 않고 플레이북 스크립트를 기본으로 해서, 데모 성공률(3곳 중 2곳 이상)을 높인다.

> **Trade-off:**
>
> - 서비스마다 한 번씩 다시 로그인해야 한다. 탈퇴는 어차피 재인증이 많아 체감 부담은 작고, 전용 프로필로 재알림 때는 로그인이 유지된다.
> - 플레이북 방식은 서비스를 늘릴수록 작성 비용이 든다. 공개 도움말을 클라우드 LLM으로 플레이북 JSON으로 만드는 방식(F-09)으로 보완한다.
> - PyInstaller 빌드는 용량이 크고 Mac은 서명·공증이 필요하다. 데모 단계에서는 감수하되, 빌드 리허설을 6일차로 당겨 마지막 날 빌드 실패 위험을 없앤다.
> - PoC는 사용자 PC에 Chrome이 설치돼 있다고 가정한다. Edge(`channel="msedge"`)나 동봉 Chromium 지원은 이후 확장한다.

> **미결 사항:**
>
> - LLM 폴백에 넘기는 링크·버튼 문구에도 이메일, 이름이 섞일 수 있다(예: "hong@gmail.com 로그아웃"). 마스킹 방식은 [논의사항 D-06](03_논의사항.md)에서 정한다.
> - 임베딩 모델을 torch 기반으로 넣으면 빌드가 GB 단위로 커질 수 있다. 6일차 빌드 리허설 결과를 보고 ONNX 런타임 전환 여부를 정한다.
> - 임베딩 모델은 한국어 메일 샘플 30건으로 2~3개 후보를 비교한 뒤 확정한다.
> - GUI는 화면이 목록·상세 수준이라 Flet으로도 충분하다. 팀원 숙련도를 보고 1일차에 최종 확인한다.
