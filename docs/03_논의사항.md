## D-01. 대표 서비스 3곳 선정

플레이북 작성(6일차), 브라우저 시연, 성공 지표("3곳 중 2곳 이상 탈퇴 화면 도달")가 모두 이 3곳에 달려 있다. 늦어도 5일차까지는 정해야 한다.

**논의할 점**
- 3곳 안에 이메일 가입, 소셜 로그인, 본인인증 요구 사례가 하나씩 들어가게 할지
- 테스트 계정을 팀원이 직접 만들 수 있는 서비스인지 (실제 탈퇴 직전까지 반복 시연해야 함)
- Gmail·네이버 메일에서 가입 메일을 쉽게 확보할 수 있는 서비스인지

---

## D-02. 도메인 제한과 소셜 로그인·본인인증

PRD는 "플레이북에 적힌 서비스 도메인 밖으로는 이동하지 않는다"고 정했다. 그런데 소셜 로그인(Google, 카카오, 네이버)과 국내 본인인증(PASS, NICE 등)은 서비스 바깥 도메인으로 이동하거나 팝업을 띄운다.

**논의할 점**
- 플레이북에 IdP·인증기관 도메인을 허용 목록으로 함께 적을지
- 바깥 도메인에서는 에이전트가 아무것도 하지 않고 사용자에게 넘기기만 할지 (넘겨주기 조건에 "허용된 외부 인증 도메인 진입" 추가)
- 팝업 창이 뜰 때 에이전트가 새 창을 어떻게 추적할지

---

## D-03. 사용자 라벨을 학습 데이터로 쓰는 방식

F-04는 "확정 / 제외 / 보류 라벨이 다음 학습 데이터가 된다"고 적혀 있다. NF-01("메일 원문은 기기 밖으로 나가지 않는다")과 함께 지키려면 방식을 정해야 한다.

**논의할 점**
- 기기 안에서만 재학습할지 (사용자별 분류기가 조금씩 달라짐)
- 라벨과 익명화된 특징만 모아 팀 모델을 개선할지 (이 경우 "외부 전송 0건" 지표의 정의를 다시 써야 함)
- PoC에서는 라벨을 SQLite에 저장만 하고, 활용 방식은 이후로 미룰지

---

## D-04. 평가 기준

성공 지표에는 재현율 80% 목표만 있고, 9일차 계획에는 정밀도도 측정하도록 되어 있다.

**논의할 점**
- 정밀도 목표를 둘지, 둔다면 몇 %로 할지 (후보가 너무 많으면 사용자가 확인을 포기함)
- 정답 계정 목록을 누구의 메일함으로, 몇 개 계정 규모로 만들지
- 합성 메일과 팀원 실제 메일을 평가에 어떻게 나눠 쓸지 (학습에 쓴 메일로 평가하지 않도록)

## D-05. 전용 프로필에 저장된 로그인 세션 보호

재알림(F-08) 때 다시 로그인하지 않도록 전용 프로필에 로그인 세션(쿠키)을 남긴다. 이 폴더가 유출되면 그 서비스들에 로그인된 상태가 그대로 넘어간다.

참고: Playwright는 macOS에서 기본으로 `--use-mock-keychain` 옵션을 넣는 것으로 알려져 있다. 이 경우 Chrome의 쿠키 암호화가 OS 키체인을 쓰지 않아 보호가 약해진다. 구현할 때 확인이 필요하다.

### 🟢 임시 확정 (2026-11-13): "필요한 동안만 보관하고, 끝나면 바로 지운다"

> PRD 5장 "지켜야 할 규칙"의 세션 보관 항목으로 반영했다. 재알림 주기(14일)는 F-08 구현 때 다시 확인한다.

| 규칙 | 내용 |
|---|---|
| 완료 즉시 삭제 | 서비스 탈퇴가 완료로 기록되면 그 서비스 도메인의 쿠키·저장소를 바로 지운다 |
| 보관 기한 | 미완료 서비스의 세션은 재알림 1회 주기(예: 14일)까지만 두고, 지나면 자동 삭제한다 |
| 전체 삭제 버튼 | 설정 화면에 "저장된 로그인 모두 지우기" 버튼을 둔다 (전용 프로필 폴더 통째 삭제) |

사용자 입장에서는 "탈퇴 끝난 곳은 바로 잊고, 남은 곳도 잠깐만 기억한다"는 규칙 하나로 이해된다.

**검토한 다른 방법**

| 방법 | 장점 | 단점 |
|---|---|---|
| 세션을 아예 저장하지 않음 | 가장 안전, 구현할 것이 없음 | 재알림 때마다 다시 로그인해야 해서 F-08의 가치가 떨어짐 |
| 프로필 폴더를 직접 암호화 | 디스크 유출에 강함 | 2주 PoC에 구현 부담이 크고, 앱 실행 중에는 어차피 복호화돼 있음 |
| Chrome 기본 쿠키 암호화에만 의존 | 추가 작업 없음 | 위 macOS 옵션 문제로 보호가 약할 수 있고, 보관 기간이 무제한 |

**선택 이유:** 새 암호화 코드 없이 파일 삭제만으로 구현돼 2주 안에 끝난다. 또 세션이 디스크에 남는 기간과 개수를 줄여서 유출 시 피해 범위를 직접 줄인다. 디스크 암호화는 정식 출시 단계에서 다시 검토한다.

## D-06. LLM 폴백에 넘기는 요소 문구 마스킹

플레이북 스크립트가 막히면 화면의 링크·버튼 요소만 추려 클라우드 LLM에 넘긴다. 계정 설정 화면에서는 요소 문구에도 이메일이나 이름이 섞일 수 있다(예: "hong@gmail.com 로그아웃").

**논의할 점**
- 이메일·전화번호 패턴을 정규식으로 `[EMAIL]`, `[PHONE]`처럼 바꿔서 보낼지
- 이름처럼 패턴이 없는 정보는 어떻게 처리할지 (사용자가 확정한 계정 정보와 일치하는 문자열 치환 등)
- 아예 로컬 모델로 처리할지 (정확도와 빌드 용량 비교 필요)
